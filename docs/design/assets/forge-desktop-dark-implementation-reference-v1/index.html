Product Flows v1.1 — continuous mission conversations
People converse with a Mission, not a naked LLM. A Mission makes its reasoning and expert structure available so the answer is better than a chat reply. One app, one Project workspace; author and operator are modes of work, not two products.
Provenance key
Current verified shipped in Forge Desktop today
Proposed intended corrective experience — designed, not built
Blocked needs a runtime contract before any UI
Shared start
Both flows begin identically

backNone — this is the root.

S2Current · destination + defaultProposed · what it offers
Missions is home
purposePlain language: work with a mission over time. Shows the selected Project and a clear mission choice.
entryAutomatic — a Project opens at Missions.

1 · Operator flow
Works with an Approved mission over many turns
1.1Current · insufficient
What I see at start
purposeProject Launcher, then Missions as home — nothing else.
entryS2.
actionRead the mission choice; pick one of the two actions.
transition→ 1.2
backHome.
Current, being corrected
Today a mission is one-shot: pick a mission → type an instruction → get a terminal run card (a completed Naive card) → open its trace. The interaction ends there. That is real and shipped, and it is insufficient — it is superseded by 1.3 below, which is the point of this revision.
↓
1.2Proposed
How I pick a mission
purposeChoose what I am conversing with — never a generic LLM chat.
entryFrom 1.1 in Missions.
actionSelect an Approved mission version to start a new conversation, or continue an existing mission conversation from the list.
transition→ 1.3 Mission Conversation
back→ Missions.
Version pinning rule
A conversation pins the mission version it started with. A newer published version is used only when a person starts a new conversation, or deliberately changes version on this one. An ongoing conversation is never silently changed.
↓
1.3Proposed · the centre of the product
Mission Conversation · persistent
purposeConverse with the mission over time. The transcript is primary.
entryFrom 1.2 — starting a new conversation or continuing an existing one.
back→ Missions (the conversation is kept, not discarded).
One turn · repeats
↻
a · I send a message
One user message is one turn. Sending it runs the mission for that turn.
b · The mission answers
A readable answer appears in the transcript, plus one compact expandable evidence card: participants, outcome, trace link. Collapsed by default — progressive disclosure.
c · I can go deeper, or just carry on
“Open trace” on the card → 1.4. Or send the next message: that continues the same conversation and creates a later turn and run. All earlier turns stay visible in the transcript.
↓
1.4Current · trace itself
Forge Trace for that one turn
purposeSee exactly what happened — durable exact participant evidence, read-only and chronological, not a summary.
entry“Open trace” on that turn’s evidence card.
actionRead it.
backMust return to the same conversation at the same turn — not merely to Missions. Proposed: today Back from a trace lands on Missions; turn-anchored return is new.
↓
1.5Proposed
End state — there isn’t a terminal one
purposeA conversation can continue indefinitely.
actionKeep sending messages.
transitionAn individual turn may be Completed or Failed without ending the conversation; a failed turn can be retried as another turn.
backStarting a new conversation is an explicit, separate action — never automatic.
2 · Author flow
Improves a mission through evaluation, then publishes it
2.1Current
What I see at start — identical
purposeThe same Project Launcher → Missions start as the operator.
entryS2.
actionNone special.
transition→ 2.2
backHome.
No author-only application, no separate install, and no mandatory role choice on launch. Authoring is a mode of work reached by an action, so the same person can move between the two flows freely.
↓
2.2Proposed
How I reach authoring
purposeGet to the mission definition itself.
entryEither the visible “Author a mission” action in Missions, or Project Explorer → the mission asset.
actionOpen the authoring document / workspace, hosted inside Project Explorer.
transition→ 2.3
back→ Project Explorer, or → Missions if entered from there.
Two things this is not
It is a proposed document destination, not a fourth rail entry — the rail stays exactly three. And Project Explorer documents are read-only today; making one editable is Proposed, not current behaviour.
↓
2.3Proposed
How I author
purposeProduce a candidate worth proving.
entryFrom 2.2.
actionOpen an existing mission, or create a candidate from an Approved version. Edit the candidate definition using grounded MCL concepts only: mission Name(input) loop(n) = { -> Expert }, when, parallel, debate.
transition→ 2.4
back→ Project Explorer. A candidate is never operator-selectable.
↓
2.4Proposed
How I say what “good” means
purposeMake quality checkable rather than felt.
entryFrom 2.3, same document.
actionDefine evaluation cases. Each names its input, its expected success and its expected failure — a mission that cannot fail correctly is not proven.
transition→ 2.5
back→ 2.3.
↓
2.5Proposed · repeats until satisfied↻
How I prove it
purposeTurn opinion into evidence.
entryFrom 2.4.
actionEvaluate the candidate against the case set → read per-case outcomes and the exact trace for each case → revise the definition or the cases → evaluate again.
transitionLoop back to 2.3 / 2.4 as needed, or → 2.6 when the evidence is good enough.
backFrom a case trace → the evaluation result it came from, then → the authoring document.
↓
2.6Proposed
How I publish
purposeMake a proven version reusable by operators.
entryFrom 2.5.
actionPromote / Publish the version as Approved.
transitionThat version becomes selectable for new operator conversations (→ 1.2).
backPublishing does not mutate any existing pinned conversation. Nobody in mid-conversation is moved onto new behaviour.
Shared evidence loop
↺
The two flows are one loop, not two products. Operator turns produce real traces and outcomes; those become author learning and feed the next candidate (→ 2.3 / 2.4). Selected Project and its evidence stay in context throughout.
Version state machine
Draft→ Candidate→ Evaluated→ Approved→ Superseded Only Approved is operator-selectable, and only for new conversations.
Actions requiring new typed shared Application.Transport contracts
create / save candidate define / store evaluations evaluate candidate list versions by state promote / publish version create / continue mission conversation submit conversation turn navigate trace → originating turn
Presentation owns rendering and navigation only. Every action above is a product action, so none of it may be UI-only behaviour.
X1Blocked
Human suspend / resume gate
Not product behaviour and not drawn in either flow. Blocked until the runtime suspend/resume contract exists: what suspends a turn, what persists while suspended, what a decision carries, and whether a suspended turn survives restart.
X2Blocked · future
Docked source · diff · inspector
Rich source-anchored panes, version diffs and a docked inspector beside the trace are future capability. A trace today is one read-only chronological document, and 1.4 shows only that.
X3Blocked · out of scope
Explicitly not designed
No dashboard, no notification inbox, no standalone Runs rail, no fourth rail entry, no editable expert registry, and no MCL construct beyond the grounded four. The named Workbench theme and token boundary is preserved in light and dark.

3a is a two-flow review artifact, not application screens: boxes stand for destinations, actions and transitions only. Nothing here is implementation authority.
